# השרת של LATISA ‏(Supabase): הקמה, מפתחות, אדמין וגיבוי

**למי:** בעל המוצר. כל הצעדים כאן נעשים ידנית, בלוח הניהול של Supabase. Claude לא נכנס לחשבון ולא מריץ שום דבר מול הפרויקט.
**עלות: 0 ₪.** תוכנית Free בלבד, בלי כרטיס אשראי. כל מה שמסומן 💳 עולה כסף: **לא לוחצים עליו.**

## 0. מה צריך לדעת לפני (אומת בתיעוד הרשמי, 2026-11-23)
- **בלי חשבון, האפליקציה עובדת בדיוק כמו 1.0.x.** החשבון רק מוסיף סנכרון ושיתוף.
- **מכסות התוכנית החינמית:**

| מכסה | ערך |
|---|---|
| פרויקטים | 2 |
| מסד נתונים | 500MB לפרויקט |
| משתמשים פעילים בחודש | 50,000 |
| אחסון קבצים | 1GB. לא בשימוש: התמונות לא עולות |
| תעבורה | 5GB, ועוד 5GB מהמטמון |

- **חריגה ממכסה:** מגיעה הודעה ותקופת חסד, ואחריהן הגבלה: השהיה, קריאה בלבד או תשובה 402. **אין חיוב בלי כרטיס.** ההגבלה מוסרת בתחילת מחזור החיוב הבא. האפליקציה ממשיכה לעבוד מהטלפון במצב "לא מחובר", ושום נתון בטלפון לא נמחק.
- **השהיה:** פרויקט עם פעילות נמוכה במשך 7 ימים מושהה. כשבוע לפני מגיע מייל אזהרה.
  - **מחזירים** בלחיצה מלוח הניהול, עד 90 יום מההשהיה (סעיף 8).
  - **אחרי 90 יום:** אפשר להוריד מהלוח קובץ גיבוי ואת הקבצים.
- **גיבויים יומיים: אין בתוכנית החינמית** (רק מ-Pro 💳). הגיבוי האמיתי: קובץ `tisa-backup` מכל טלפון, וייצוא CSV מהלוח (סעיף 9).
- **מייל:** שירות המייל המובנה שולח רק לחברי הצוות של הארגון ב-Supabase, ובקצב נמוך.
  - **לכן (החלטה, אפשרות א'):** בלי אישור מייל בהרשמה, ואיפוס סיסמה לחברים נעשה ידנית (סעיף 6).
  - **מה לא מפעילים:** SMTP חיצוני ו-SMS 💳. דורשים החלטה נפרדת.
- **האזור (Frankfurt) נבחר פעם אחת ולא משתנה.**
  - מעבר אזור = פרויקט חדש, העברת נתונים, וגרסה חדשה של האפליקציה.
  - כל משתמש יצטרך להיכנס מחדש. הנתונים בטלפונים לא נפגעים.

## 1. פתיחת חשבון ופרויקט
1. נכנסים ל-supabase.com ונרשמים. **לא מוסיפים כרטיס אשראי.**
2. יוצרים ארגון (Organization) בתוכנית **Free**.
3. **New project:**
   - **Name:** למשל `latisa`.
   - **Database Password:** סיסמה חזקה. **שומרים אצלכם בלבד**: לא בצ'אט, לא ב-Git ולא במייל. האפליקציה לא צריכה אותה.
   - **Region:** בוחרים אזור **ספציפי**: `Central EU (Frankfurt)`, כלומר `eu-central-1`. לא "General region".
   - 💳 לא משנים Compute size ולא מוסיפים add-ons.
4. מחכים שהפרויקט יעלה (כמה דקות).

## 2. הגדרות כניסה (Authentication)
1. **Authentication › Sign In / Providers › Email:**
   - Email פעיל.
   - **Confirm email: כבוי** (החלטה א'). ההגנה: משתמש חדש מתחיל "ממתין" ולא רואה כלום עד שאתם מאשרים.
2. **Phone:** כבוי. 💳 SMS עולה כסף.
3. **Password:** אם יש הגדרת אורך מינימלי, קובעים **8**. האפליקציה דורשת 8 בכל מקרה.
4. **Authentication › URL Configuration:**
   - **Site URL:** `https://mosheuzan01-ops.github.io/tisa-trip-os/`
   - **Redirect URLs:** מוסיפים את אותה כתובת.
5. **לא מפעילים:** Custom SMTP, ‏Phone, ‏CAPTCHA בתשלום, Custom Domain 💳.

## 3. יצירת הטבלאות וההרשאות (פעם אחת)
1. **SQL Editor › New query.**
2. מעתיקים את **כל** הקובץ `supabase/migrations/0001_stage14_init.sql` מהענף, ולוחצים **Run**.
3. מצופה: `Success. No rows returned`.
4. אם יש שגיאה, לא מריצים שוב חלקים. שולחים את השגיאה כמו שהיא.

## 4. בדיקת ההרשאות האמיתית (RLS)
1. **SQL Editor › New query.** מעתיקים את **כל** הקובץ `supabase/tests/rls_check.sql`, ולוחצים **Run**.
2. **מצופה:** הודעת **ERROR** שבה כתוב `RLS CHECK RESULT: 53 PASS, 0 FAIL`.
   - ה-ERROR בכוונה: הוא מבטל את כל מה שהבדיקה יצרה (5 משתמשי בדיקה, טיול ורשומות), ולא נשאר כלום.
3. מצלמים את המסך ושולחים. זו הראיה ל-S14-3 בפרויקט האמיתי.
4. **אם יש שורות `FAIL:`:** לא מחברים את האפליקציה. שולחים את הצילום.
5. 🔎 **לא נבדק מול פרויקט אמיתי:** הבדיקה רצה מקומית על PostgreSQL 16, עם תחליף לסכמת ה-auth (‏53/53). ייתכן שבפרויקט אמיתי תוספת לטבלת `auth.users` תדרוש עמודה נוספת. אם כן, תופיע שגיאה ברורה. שולחים אותה כמו שהיא, ואתקן.

## 5. חיבור האפליקציה
1. **Project Settings › API Keys** (או **API**): מעתיקים **רק שני דברים**:
   - **Project URL:** `https://<20 תווים>.supabase.co`
   - **Publishable key** (`sb_publishable_...`), או ה-**anon public** הישן.
2. **מה אסור:** ה-**secret** (`sb_secret_...`) או ה-**service_role**. אסור להעתיק אותם, לשלוח אותם או להכניס אותם לשום קובץ.
3. את שני הערכים אפשר לשלוח לי או להכניס בעצמכם ל-`config/app.config.json`:
   ```json
   "cloud": { "url": "https://<ref>.supabase.co", "publishableKey": "sb_publishable_..." }
   ```
   - הם **ציבוריים מטבעם** ונמצאים בקוד הלקוח. ההגנה היא ה-RLS מסעיף 4.
   - הבדיקה `tests/stage14-rules.test.js` (S14-8c) נכשלת אם מוכנס שם מפתח אחר.
4. אחרי שהשינוי ממוזג, הוא נכנס לגרסה הבאה. מקבלים אותו באתר כמו כל עדכון.

## 6. אדמין, אישור משתמשים, חסימה ואיפוס
- **הפיכה לאדמין (רק ידני, רק אתם):**
  1. נרשמים באפליקציה עם המייל שלכם. החשבון "ממתין".
  2. ב-SQL Editor מריצים שורה אחת, עם המייל שלכם במקום הטקסט. **לא שומרים אותה בקובץ במאגר:**
     ```sql
     update public.profiles set role = 'admin', status = 'approved' where email = lower('YOUR-EMAIL-HERE');
     ```
  3. טוענים את האפליקציה מחדש. בכרטיס "החשבון והטיולים שלי" מופיע **"ניהול"**.
  - אין דרך ליצור אדמין מתוך האפליקציה. גם אדמין לא יכול לשנות `role`. זה נבדק ב-M07 וב-N04.
- **אישור משתמש חדש:** "ניהול" › המשתמש › **אישור**. רק אחרי האישור הוא מתחיל לסנכרן.
- **חסימה:** "ניהול" › **חסימה** › אישור.
  - המשתמש החסום מאבד מיד גישה לכל נתון בשרת, גם לטיולים ששותפו איתו.
  - הנתונים בטלפון שלו לא נמחקים.
- **הסרת חבר מטיול:** בעל הטיול, ב"חברי הטיול", או האדמין, ב"ניהול" › טיולים.
- **איפוס סיסמה לחבר (ידני):**
  1. ב-SQL Editor:
     ```sql
     update auth.users set encrypted_password = extensions.crypt('Temp-Pass-123!', extensions.gen_salt('bf')) where email = lower('FRIEND-EMAIL');
     ```
  2. מוסרים לחבר את הסיסמה הזמנית בעל-פה. אחרי הכניסה הוא בוחר סיסמה חדשה ב"החשבון והטיולים שלי" › **"שינוי סיסמה"**.
  3. 🔎 הפקודה מבוססת על `pgcrypto`, שקיים בפרויקטים של Supabase, אבל לא נבדקה מול פרויקט אמיתי. אם יש שגיאה, שולחים אותה.
- **איפוס לעצמכם:** "שכחתי סיסמה" שולח קישור למייל, כי אתם חברי הצוות בארגון.

## 7. מחיקה מלאה של משתמש (דורשת את המפתח הסודי, לכן רק בלוח הניהול)
1. מבקשים מהמשתמש לייצא גיבוי מהטלפון, אם הוא רוצה לשמור משהו.
2. **Authentication › Users** › בוחרים את המשתמש › **Delete user**.
3. **מה נמחק מהשרת:**
   - הפרופיל.
   - הטיולים **שבבעלותו**, כולל כל הרשומות שלהם, וגם החלק שחברים ראו.
   - החברות שלו בטיולים של אחרים.
   - הרשומות האישיות שלו.
4. **מה לא נמחק:** העותקים שכבר נמצאים בטלפונים, שלו ושל חבריו.
5. **שימו לב:** אם הוא בעל טיול משותף, הטיול נעלם לחברים מהשרת. אצלם הוא נשאר כעותק "במכשיר בלבד".

**מחיקת טיול אחד מהענן:** אין כפתור כזה באפליקציה, בכוונה: האפליקציה לא מוחקת כלום בשרת, רק מסמנת מחיקה של פריטים.
1. **Table Editor › `trips`** › השורה של הטיול › **Delete**.
2. החברויות והרשומות שלו נמחקות איתו (cascade).
3. העותקים בטלפונים נשארים, ומסומנים "במכשיר בלבד".

## 8. השהיה (Pause) ואיך מחזירים
- **סימנים:** מייל "Your project will be paused", ובאפליקציה הנקודה האדומה והטקסט "לא מחובר".
- **מחזירים:** לוח הניהול › הארגון › הפרויקט › **Resume project**, ומאשרים. אחרי כמה דקות האפליקציה מסנכרנת לבד.
- **בזמן ההשהיה:** הכול עובד מהטלפון. שינויים ממתינים ונשלחים אחרי ההחזרה.
- **אחרי 90 יום של השהיה:** כבר אי אפשר להחזיר בלחיצה. אפשר להוריד מהלוח את קובץ הגיבוי ואת הקבצים, ולשחזר לפרויקט חדש. במקרה כזה הטלפונים ממשיכים לעבוד עם הנתונים שלהם.
- **איך לא להגיע להשהיה:**
  - **מותר:** שימוש רגיל באפליקציה בכמה מכשירים, או כניסה לוח הניהול, משאירים את הפרויקט פעיל.
  - 💳 **אסור:** שדרוג ל-Pro. הוא מבטל השהיה, אבל עולה כסף.
